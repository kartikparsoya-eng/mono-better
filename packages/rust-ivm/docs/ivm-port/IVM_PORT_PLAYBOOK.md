# IVM Port Playbook — how to use extractions #1–#7

**Read this first, every session.** These seven artifacts are the guardrails for
porting the TS IVM (`mono-v1.7/packages/zql/src/ivm/`) to Rust (`rust-ivm/`).
They are the source of truth. Do not "fix" a mismatch by editing an artifact or a
`.expected.json` — the TS engine is the oracle; the Rust engine must match it.

---

## The core loop (do this for every change)

```
1. Make a Rust change (port an operator, fix a bug).
2. cargo clean -p rust-ivm      # MANDATORY — a stale .rlib hides real divergences
3. cargo test --test fixture_replay_test     # #1 — must stay green
   cargo test --test property_laws_test      # #6 — must stay green
4. If you fixed a divergence, move its fixture regressions/ -> fixtures/
   (input.json + expected.json) so it becomes a permanent passing test.
5. Never hand-edit *.expected.json. Regenerate only via ts-runner.mjs.
```

If `fixture_replay_test` goes red, you regressed something. If a `regressions/`
fixture now passes, you fixed a divergence — promote it.

---

## Debugging a divergence — the pipeline trace harness

When a fixture diverges, don't guess — **trace the actual push/fetch flow.**
There's an env-gated tracer built in (`src/ivm/trace.rs`, zero cost when off).

```
FIX=<fixture-name> IVM_TRACE=1 cargo test --test trace_fixture -- --nocapture
```
`FIX` resolves against both `agentic/fixtures/` and `.../regressions/` (defaults
to `seed-159916`). Output is one line per push each routing operator receives:
```
[ivm-trace] <op>#<n>   recv  <change>
```
- `<op>` = the operator (`join`, `fan_in`, `exists`, `node_filter`, `catch`, …);
  `#n` distinguishes adapters (`join#1` = ParentOutput, `join#2` = ChildOutput).
- Read the emit→recv chain top-to-bottom to see who transformed what. A change
  that should become an `ADD` but shows up at `catch` as a `CHILD` (or vice
  versa) points straight at the operator that mis-routed it.

This tool localized every hard regression this project fixed (OR-with-EXISTS
wiring, FlippedJoin comparator, Exists cache). Add `trace::emit(...)` at an
operator's `output.push(...)` sites if you also need to see emits, not just
receives. Full guide + a worked example: **`IVM_TRACE_HARNESS.md`**.

## #1 — Fixture oracle  (`IVM_FIXTURE_ORACLE.md`)
**What it is:** input→expected fixtures generated by the TS engine; Rust replays
and must match byte-for-byte. `agentic/fixtures/` = must-pass;
`agentic/fixtures/regressions/` = known divergences (the port backlog).

**Use it to:**
- **Know if the port is correct:** `cargo test --test fixture_replay_test`.
- **Pick the next bug:** each file in `regressions/*-push-*` is a failing case.
  Its name tells you the operator + scenario.
- **Add coverage for a new TS test file:**
  ```
  cd rust-ivm/agentic
  node --experimental-strip-types oracle/capture.mjs \
    ../../mono-v1.7/packages/zql/src/ivm/<file>.test.ts --out fixtures/_captured
  for f in fixtures/_captured/*.input.json; do \
    node --experimental-strip-types oracle/ts-runner.mjs "$f"; done
  # replay each; passing -> fixtures/, diverging -> fixtures/regressions/
  ```
- **Rule:** expected output comes ONLY from `ts-runner.mjs`. Never write it by hand.

## #2 — Assertion catalog  (`IVM_ASSERTION_CATALOG.md`)
**What it is:** all 85 TS `assert()` contracts + whether Rust enforces each.

**Use it to:** when porting or reviewing an operator, open the catalog, find that
file's rows, and make sure every 🔴 is either added as a Rust `assert!`/
`debug_assert!` or consciously waived (⚪ rows explain the exceptions). Start with
the "High" gaps: join key-length, edit-keeps-join-key, Take/Cap early-return,
MemorySource existence.

## #3 — Change-type table  (`IVM_CHANGE_TYPE_TABLE.md`)
**What it is:** how each operator maps ADD/REMOVE/EDIT/CHILD → output.

**Use it to:** before writing or debugging an operator's `push()`, read its row.
The table also **maps each divergence cluster to a specific cell** — so when you
pick an exists/cap/take/flipped divergence from `regressions/`, this tells you
exactly which transition to fix (e.g. Exists CHILD 0↔1 → `exists.ts:139-185`).

## #4 — Builder rules  (`IVM_BUILDER_RULES.md`)
**What it is:** which operator the builder instantiates for which AST.

**Use it to:** whenever you touch `rust-ivm/src/builder/`. The wrong pipeline
*shape* can't be fixed at the operator level. Key trap: the `useCap` (Cap-vs-Take)
decision and the EXISTS `limit:0` dead-query.

## #5 — Reset paths  (`IVM_RESET_PATHS.md`)
**What it is:** the 5 `ResetPipelinesSignal` reasons + the advancement-timeout
algorithm.

**Use it to:** when touching advance / snapshotter / diff. Rust emits 3 of 5;
the open gaps are `scalar-subquery` emission (add it) and confirming the driver
enforces the timeout algorithm. A missing reason = silent stale results.

## #6 — Property laws  (`rust-ivm/tests/property_laws_test.rs`)
**What it is:** proptest laws for `compare_values`/`values_equal` (reflexivity,
antisymmetry, transitivity, null ordering, null exclusion, equal-consistency).

**Use it to:** run `cargo test --test property_laws_test` after ANY change to
`data.rs` comparison/value code. If you add a `Value` variant or change ordering,
extend these laws.

## #7 — Serialization contract  (`IVM_SERIALIZATION_CONTRACT.md`)
**What it is:** every type crossing napi + the SQLite→Value mapping.

**Use it to:** when touching `napi/src/lib.rs` or `src/sqlite/`. Known fix: the
i64→f64 conversion at `table_source.rs:470/593` + `napi/src/lib.rs:266` must
add a `±2^53` bounds check that ERRORS (matching TS `UnsupportedValueError`),
not silently truncate.

## Hard rules (repeat to the agent)
1. `cargo clean -p rust-ivm` before trusting the fixture suite.
2. Never edit `.expected.json` or an artifact to make a test pass.
3. A fixed divergence = fixture moved `regressions/` → `fixtures/`, suite green.
4. The TS engine is the oracle. Rust conforms to TS, not the reverse.
