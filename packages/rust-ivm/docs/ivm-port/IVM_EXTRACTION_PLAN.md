# What Else to Extract from TS Before More Rust Porting

The lifetime doc was one extraction. Here are six more categories of
information baked into the TS source that, if extracted up front, will
prevent re-port cycles. Each is quantified with counts from the actual source.

---

## 1. Assertion Catalog (85 contracts)

The TS IVM has **85 `assert()` calls** in non-test code. Each is a correctness
contract — a precondition, postcondition, or invariant that must hold. If the
Rust port misses one, you get **silent drift** (wrong results, no crash) or
**late panic** (crash in production, not in testing).

### Why this matters
The audit found that the Rust port is missing several assertions:
- `Join`/`FlippedJoin` don't assert `parent !== child` (Invariant #6)
- `Take` doesn't assert "no downstream early return during initialFetch"
- `Cap` doesn't assert the same
- `Join` doesn't assert `parentKey.length === childKey.length` in the constructor

Each missing assert is a potential silent-corruption path.

### What to extract
A table of every `assert()` with: file, line, condition, what it guards, and
the Rust equivalent. Example:

| File:Line | Assertion | Guards | Rust status |
|---|---|---|---|
| `join.ts:73` | `parent !== child` | Join with itself = infinite recursion | 🔴 missing |
| `join.ts:74` | `parentKey.length === childKey.length` | Malformed AST | 🔴 missing |
| `take.ts:159` | `req.start === undefined` | Take doesn't support start in initialFetch | 🔴 missing |
| `take.ts:210` | `!downstreamEarlyReturn` | State not hydrated if early return | 🔴 missing |
| `cap.ts:88` | `!req.start` | Cap doesn't support start | 🟢 present |
| `memory-source.ts:469` | `added` (row insert succeeded) | Duplicate row in source | 🔴 missing |
| `push-accumulated.ts:108` | `!candidates.has(type)` | Multiple same-type changes from one branch | 🟢 present |

**85 rows total.** This is a 2-hour extraction pass that prevents dozens of
subtle bugs.

## 2. Test Fixture Extraction (1,790 assertions as oracle)

The TS test suite has **61,137 lines of tests** across 30+ files, containing
**~1,790 assertions**. These encode the exact expected behavior for every
operator under every input. This is your **differential testing oracle**.

### The test harness pattern

The TS tests use a shared harness (`test/fetch-and-push-tests.ts`):
```ts
runPushTest({
  sources: { testTable: { columns, primaryKeys } },
  sourceContents: { testTable: [...rows] },
  ast: <AST>,
  format: <Format>,
  pushes: [[tableName, SourceChange], ...],
}) → { data, pushes, storage, log }
```

This harness:
1. Creates sources, pre-loads rows
2. Builds the pipeline from AST
3. Hydrates (fetch)
4. Applies pushes in sequence
5. Returns the final view state + pushed changes + storage state

### What to extract

Convert each `runPushTest` / `runFetchTest` call into a **language-independent
JSON fixture**:
```json
{
  "sources": { "testTable": { "columns": {...}, "primaryKey": ["id"] } },
  "sourceContents": { "testTable": [{"id": "i1", "created": 100}] },
  "ast": { "table": "testTable", "orderBy": [["created", "asc"]], "limit": 5 },
  "format": { "singular": false },
  "pushes": [ ["testTable", { "type": "add", "row": {"id": "i4", "created": 50} }] ],
  "expected": {
    "data": [...],
    "pushes": [...],
    "storage": {...}
  }
}
```

The `expected` output is generated by **running the TS engine** (the oracle).
The Rust engine must match byte-for-byte.

### Counts by operator

| Test file | Tests | Lines | Priority |
|---|---|---|---|
| `take.push.test.ts` | 49 | 8,128 | P0 (was stub) |
| `join.push.test.ts` | 43 | 10,063 | P1 |
| `flipped-join.push.test.ts` | 45 | 10,429 | P1 |
| `source.test.ts` | 96 | 4,147 | P1 |
| `cap.push.test.ts` | 23 | 1,964 | P2 |
| `exists.push.test.ts` | 25 | 2,326 | P2 |
| `view-apply-change.test.ts` | — | 2,651 | P2 |
| `memory-source.test.ts` | 39 | 1,197 | P2 |
| All fetch tests | 114 | ~8,000 | P2 |

**The `RUST-IVM-GOAL.md` Phase 1 already calls for this** — but extracting the
fixtures is a mechanical pass that can be done now, before writing more Rust
code. It's the single highest-leverage thing you can do: it turns "does the
Rust port work?" from a guess into a checkbox.

## 3. Per-Operator Change-Type Transformation Table

Each operator transforms incoming `Change` types in specific ways. This is the
**push protocol** — getting it wrong means wrong downstream results.

### What to extract

A matrix of `operator × input_change_type → output_change_type(s)`:

| Operator | ADD in | REMOVE in | EDIT in | CHILD in |
|---|---|---|---|---|
| **Filter** | ADD (if pred) | REMOVE (if pred) | ADD/REMOVE/EDIT (split on pred) | CHILD (if pred) |
| **Skip** | ADD (if in range) | REMOVE (if in range) | ADD/REMOVE/EDIT (split on range) | CHILD (if in range) |
| **Take** | ADD or REMOVE+ADD (if full & new < bound) | REMOVE or REMOVE+ADD (refill) | EDIT/REMOVE+ADD/REMOVE+EDIT (4 cases × 3 positions) | CHILD (if ≤ bound) |
| **Cap** | ADD (if under limit) | REMOVE or REMOVE+ADD (refill) | EDIT (if in PK set) | CHILD (if in PK set) |
| **Join** (parent) | ADD (with child rel) | REMOVE (with child rel) | EDIT (assert key unchanged) | CHILD (with child rel) |
| **Join** (child) | CHILD (to all matching parents) | CHILD (to all matching parents) | CHILD (assert key unchanged) | CHILD (nested) |
| **FlippedJoin** (parent) | ADD (if has child) | REMOVE (if has child) | EDIT (assert key unchanged) | CHILD (if has child) |
| **FlippedJoin** (child) | ADD or CHILD | REMOVE or CHILD | CHILD | CHILD (nested) |
| **Exists** | passthrough (if pred) | passthrough (if pred) | passthrough (if pred) | ADD/REMOVE/passthrough (on 0↔1 transition) |
| **FanOut** | fan to all branches | fan to all branches | fan to all branches | fan to all branches |
| **FanIn** | accumulate → collapse | accumulate → collapse | accumulate → collapse | accumulate → collapse |

This is derivable from reading each `push()` method, but having it as a lookup
table prevents misinterpreting the control flow during porting.

### The EDIT-splitting rules (most error-prone)

Three operators split edits into add/remove pairs:
1. **Filter**: `old_present && !new_present → REMOVE; !old_present && new_present → ADD`
2. **Skip**: same logic, `should_be_present` as predicate
3. **Take**: 12 sub-cases based on old/new position relative to bound

The Take edit state machine alone has **4 top-level cases × 3 positions = 12
paths**, each with different output (edit, remove+add, remove+edit). This is
the single most complex control flow in IVM and should be extracted as an
explicit transition table.

## 4. Builder AST → Operator-Tree Mapping Rules

The builder (`builder.ts:buildPipelineInternal`) decides which operators to
instantiate based on AST properties. Getting these rules wrong means the wrong
pipeline shape → wrong results.

### Decision rules to extract

| Condition | Operator | Rule |
|---|---|---|
| `ast.start` present | `Skip` | Always |
| `ast.limit !== undefined && isNonFlippedExistsChild && no flipped subqueries` | `Cap` | Cap (unordered, no sort) |
| `ast.limit !== undefined && (not exists child || has flipped subqueries)` | `Take` | Take (ordered, sort required) |
| Correlated subquery, `flip: false`, fromCondition | `Join` | Normal join |
| Correlated subquery, `flip: true` | `FlippedJoin` | Flipped (child drives parent) |
| Correlated subquery, `op: EXISTS/NOT EXISTS`, `limit: 0` | `Filter(() => false/true)` | Dead query |
| `where` has OR with subqueries | `FanOut` + `FanIn` | OR expansion |
| `where` has OR with flipped subqueries | `UnionFanOut` + `UnionFanIn` | Union expansion |
| `ast.related` | `Join` (if limit > 0 or not fromCondition) | Relationship join |
| EXISTS limit | `3` (client) / `1` (permissions) | Constant |
| Permissions EXISTS limit | `1` | Constant |

Also extract: `splitEditKeys` computation (which keys trigger edit splitting at
the source level).

### Why this matters
The Rust builder currently has a simplified version. Missing the Cap-vs-Take
decision, or the UnionFanOut path, means the wrong pipeline shape. This is
structural — no amount of operator-level correctness fixes a wrong pipeline.

## 5. ResetPipelinesSignal Recovery Paths

The TS code has **5 reset reasons**, each with a different recovery path:

```ts
type ResetPipelinesReason =
  | 'advancement-timeout'    // advance took too long → rebuild
  | 'scalar-subquery'        // scalar subquery value changed → rebuild
  | 'schema-change'          // SQLite schema changed → rebuild all
  | 'truncation'             // table truncated → rebuild
  | 'permissions-change';   // permissions changed → rebuild
```

### What to extract
For each reason:
1. **What triggers it** (which code path throws)
2. **What state must be cleared** (pipelines, tables, storage, row-set signatures)
3. **What state is preserved** (which sources survive, which connections stay)
4. **The recovery flow** (re-init → re-hydrate all queries from current SQLite)

The Rust port currently has `ResetPipelinesSignal` but doesn't differentiate
reasons. Missing a reason means a recovery path that silently doesn't fire →
stale results after schema changes or truncations.

Also: the `advance` timeout logic (compare elapsed time to total hydration time,
abort at half/half) is a specific algorithm that should be extracted verbatim.

## 6. Property-Based Test Laws

The TS tests use `fast-check` (property-based testing) for algebraic laws. These
are **executable specifications** — they encode mathematical properties that
must hold for any input, not just hand-picked cases.

### What to extract

| Law | File | Property |
|---|---|---|
| `compareValues` reflexivity | `data.test.ts` | `compareValues(a, a) === 0` |
| `compareValues` antisymmetry | `data.test.ts` | `compareValues(a, b) === -compareValues(b, a)` |
| `compareValues` null ordering | `data.test.ts` | `null < everything except null` |
| `valuesEqual` null exclusion | `data.test.ts` | `valuesEqual(null, x) === false` always |
| Comparator transitivity | `compare-rows-test.ts` | if `a < b && b < c` then `a < c` |
| Comparator stability | `compare-rows-test.ts` | `compare(a, b) === 0` implies order preserved |

These laws should be ported to Rust `proptest` or `quickcheck` tests. They catch
bugs that unit tests miss because they test random inputs. The Rust port
currently has **no property-based tests**.

## 7. Serialization Boundary Contract (napi)

The napi crate (`napi/src/lib.rs`) converts between TS and Rust types. This
conversion must be **exact** — any mismatch causes silent data corruption at
the boundary.

### What to extract
A mapping table of every type that crosses the boundary:

| TS type | Wire format | Rust type | Conversion notes |
|---|---|---|---|
| `Value` | `NapiValue { kind, bool_val, f64_val, str_val, json_val }` | `enum Value` | Kind tag must match exactly |
| `Row` | `HashMap<String, NapiValue>` | `Arc<FxHashMap<String, Value>>` | Key order doesn't matter (HashMap) |
| `Change` | `NapiRowChange { change_type: i32, ... }` | `enum Change` | `change_type` int must match `ChangeType` repr |
| `AST` | JSON string (camelCase) | `TsAst` → `Ast` | `#[serde(tag="type", rename_all="lowercase")]` |
| `Condition` | tagged union `{ type: "simple" | "and" | "or" | "correlatedSubquery" }` | `TsCondition` | Internal tagging |
| `OrderPart` | `[string, string]` tuple | `(String, String)` | Direction is "asc"/"desc" |
| `Bound` | `{ row, exclusive }` | `TsBound` | Row is a full Row object |
| `CorrelatedSubquery` | `{ correlation: { parentField, childField }, subquery, system, hidden }` | `TsCorrelatedSubquery` | camelCase field names |
| `SourceChange` | `{ type: "add"/"remove"/"edit", row, old_row }` | `SourceChange` | Inferred from napi push path |

### The SQLite type conversion (最容易出错)

```
SQLite Integer → Value::F64(n as f64)     // ❌ loses precision for large ints!
SQLite Real    → Value::F64(n)
SQLite Text    → Value::Str(Arc<str>)
SQLite Blob    → Value::Str(String::from_utf8_lossy)  // lossy!
SQLite Null    → Value::Null
```

The TS impl uses `safeIntegers(true)` and handles bigint separately. The Rust
impl casts `i64 → f64` which **loses precision above 2^53**. This is a real bug
for any table with large integer IDs.

## Recommended Extraction Order

| Priority | Extraction | Effort | Impact |
|---|---|---|---|
| 1 | Test fixtures (JSON, oracle-generated) | High but mechanical | Eliminates "does it work?" guessing |
| 2 | Assertion catalog (85 asserts) | Low (2h grep + table) | Prevents silent corruption |
| 3 | Per-operator change transformation table | Medium (read each push) | Prevents push-protocol bugs |
| 4 | Builder AST→operator rules | Medium (one file) | Prevents wrong pipeline shape |
| 5 | Serialization boundary contract | Medium (one crate) | Prevents boundary data loss |
| 6 | ResetPipelinesSignal paths | Low (5 reasons) | Prevents stale results after recovery |
| 7 | Property-based test laws | Low (6 laws) | Catches edge cases unit tests miss |

The test fixtures (#1) are by far the highest leverage — they turn the entire
port from "interpret and hope" into "match the oracle." The assertion catalog
(#2) is the cheapest and prevents the most subtle bugs. Do both before any more
operator implementation work.
